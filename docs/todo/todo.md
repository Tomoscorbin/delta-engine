A `condition` field on the failure types would therefore require parsing the message head on the warehouse path; decide separately whether that is worth it alongside PySpark's `getCondition()` on the Spark path.

- [ ] Compile empty column comments as `COMMENT ''` — SQL warehouses reject `ALTER TABLE ... ALTER COLUMN ... UNSET COMMENT` (verified live 2026-07-12). The fix (drop the UNSET branch in the SQL compiler) was reverted out of the live-suite PR #213 to keep it test-only; reapply it as its own fix PR, and restore the empty-comment transition in the lifecycle live test (`account_code` in `test_sync_changes_every_mutable_table_aspect_in_live_catalog`) when it lands.
- [ ] The reader cannot round-trip struct field names containing special characters (found by the live suite 2026-07-12). With column mapping, the declaration gate and compiler happily create `s STRUCT<`bad name`: INT>`, but information_schema renders the type unquoted (`struct<bad name:int>`), the shared type parser skips the column as unrecognised (with a warning), and the next sync plans an `ADD COLUMN s` that fails `FIELD_ALREADY_EXISTS`. Either teach the parser quoted/special-character field names or make the declaration gate reject special characters in NESTED field names regardless of column mapping until the round trip works.
- [x] Renames need an identity signal beyond the name (parked 2026-07-08). RESOLVED 2026-07-12 via the `renamed_from` hint on `Column`: the differ relabels the observed column through the hint and emits `RenameColumn` directly; the hint is inert once applied. An ambiguous declared rename (old and new both present) is the non-action `ColumnRenameConflict` difference rejected by the `AmbiguousColumnRename` policy rule; editing a name directly without the hint is taken literally as `DropColumn` plus `AddColumn` (no rename guessing). Table renames would extend the same mechanism (`renamed_from` on `DeltaTable`), not yet built.
- [ ] Live-workspace verification for column renames (implemented 2026-07-12, branch `feat/renamed-from`): (1) confirm Unity Catalog column tags and comments physically travel with `ALTER TABLE ... RENAME COLUMN` (expected yes; tag drift self-heals on the next sync regardless because tags are full-state); (2) confirm the error shapes when a CHECK constraint or generated column references the renamed column (Databricks docs say these must be changed for the rename to proceed — the engine does not model them, so they surface as execution errors per the no-preflight policy); (3) confirm that suppressing the PK/FK drops handled atomically by `RENAME COLUMN` does not also silently drop **other** tables' foreign keys beyond what `PrimaryKeyReferencedByForeignKeys` already blocks. Add a walkthrough step exercising a successful rename (including a PK-column rename) so the manual suite covers it.
- [ ] Cross-catalog inbound foreign keys are invisible to `PrimaryKeyReferencedByForeignKeys` (information_schema is per-catalog), so a cross-catalog referenced PK drop still fails at execution rather than validation. Decide whether that is acceptable long-term or worth probing the referencing catalogs (cost: catalog reads fan out). The outbound direction is rejected at declaration for the same reason (`ForeignKey` requires the referenced table to share the owner's catalog); lifting either restriction means resolving the parent side from the parent's catalog or the metastore-wide `system.information_schema`.
- [ ] Watch the inbound-FK read cost: observing referencing foreign keys adds one information_schema query per table read (PR #152). No latency evidence yet — do not optimize without it; if large syncs hurt, batch the metadata reads per catalog rather than per table.
- [ ] Release notes for the next release must call out the stricter property values: previously-accepted declarations like `"True"`, `"1_000"`, or compound intervals (`interval 1 hour 30 minutes`) now fail at declaration time with messages naming the expected format. Also call out two breaking declaration changes from the FK-pairing redesign: `primary_key` moved from a per-column `Column(primary_key=True)` flag to a `DeltaTable(primary_key=[...])` parameter, and `ForeignKey(columns={local: referenced})` replaces the positional `local_columns=[...]` list. Both old forms fail loudly at construction (unexpected keyword argument, or a missing/extra-column `ValueError`) rather than silently changing meaning. Also call out: `delta.enableTypeWidening` is now a managed key — per the registry admission policy this is breaking, since tables with the key set but undeclared start failing validation (`PropertyMustBeDeclared`) on upgrade.
- [ ] add unique columns: ALTER TABLE U ADD CONSTRAINT u_uq_email UNIQUE(email);
- [ ] Make the application layer backend-agnostic, not just backend-library-free. Today the `backend-imports-stay-in-adapters` contract only forbids importing the `delta`/`pyspark` _packages_; the application layer still hardcodes Delta-family _policy_ — the safe-change rules (`PartitioningChangeNotSupported`, `ColumnDataTypeChangeNotSupported`, `NonNullableColumnAdd`, `ColumnMappingRequiredForDrop`) exist because Databricks/Delta rejects those operations, and `application/properties.py` holds the Delta property catalogue (`DELTA_PROPERTY_REGISTRY`, `COLUMN_MAPPING_MODE_KEY`, `delta.*` key strings) consumed by `validation.py`, `api/properties.py`, and the reader. The layering is sound for now (application is the only layer all three consumers can reach without violating the `adapters|api → application → domain` order), but it means "backend-agnostic" is only half true. The real refactor: `application` holds only the _mechanism_ (how rules run, the `Rule` protocol, how `validate_diff` composes them), and the backend _specifics_ (which rules, which property keys and their restrictions) are injected from the composition root or an adapter-provided port. This must move ALL the backend-flavoured rules and the property catalogue together — moving only the property pieces just relocates a third of the problem. Larger change, own PR. See the property-ownership spec addendum for how the registry ended up in application.

- [ ] Decide whether to emit `RELY` on FK/PK constraints. Without `RELY`, Databricks treats informational constraints as documentation only and the optimizer cannot use them for join elimination / query rewrite. If the point of declaring keys is optimization, they are currently inert. Weigh against the risk of `RELY` on unverified data (the optimizer trusts it). Would add a `rely: bool` to `ForeignKeyConstraint`/`PrimaryKeyConstraint` and a ` NOT ENFORCED RELY` / ` NOT ENFORCED` suffix in the compiler.
