# Open questions and decisions

- [ ] Create external tables. The read boundary accepts existing external Delta tables (PR #249) and every planned action is a location-agnostic ALTER that reconciles them like managed ones, but the engine cannot create one: `DeltaTable` has no way to declare a location and `compile_create_table` emits no `LOCATION`, so a declared table that is absent is always created managed. Needs a declaration surface, compiler support, validation thought (location drift?), and live coverage against a workspace with an external location.
- [ ] Databricks reader now reads via `DESCRIBE TABLE EXTENDED … AS JSON` (2026-07-15; per-table round trips ~8→4, both backends share one JSON parser + assembly). Effects on items below: **(7)** struct field names with special characters now round-trip — the JSON reports field names as strings rather than embedded in DDL text, so the parser no longer skips them; keep #7 open only to confirm live, and the declaration-gate workaround is unnecessary. **(4)** struct field nullability is now carried by the AS JSON source (`fields[].nullable`), so modeling it is gated on the domain `StructField` type, not the observation source. **R1 (verify live before relying on it):** managed properties are read from AS JSON's `table_properties` (registry-filtered), and an observed-but-undeclared registry property is a hard validation failure — confirm on a live workspace that `table_properties` never synthesizes a default for any of the 6 registry keys when unset (especially `logRetentionDuration` / `deletedFileRetentionDuration`, which the sampled tables did not exercise); fallback is to read that property from `DESCRIBE DETAIL`. Also confirm `table_constraints` never carries CHECK/UNIQUE bodies (the parser skips unrecognized constraint types rather than failing the read).
- [x] Live-workspace verification of the warehouse backend (PR #206). DONE 2026-07-12 via the live suite (`uv run pytest tests/live -m databricks_e2e --no-cov`, all green against Unity Catalog): (1) information_schema saw just-created tables within one sync — the create-then-resync idempotency test passed with no stale absence; (2) PK/tag/property rows flowed correctly through the shared `sql/rows.py` mappers across the whole suite; (3) deliberate failure probe: `ServerOperationError` exposes NO structured SQLSTATE/condition attribute in connector 4.x — the error condition appears only as the bracketed message prefix (e.g. `[DELTA_FEATURES_REQUIRE_MANUAL_ENABLEMENT] ...`), and `context` carries only `diagnostic-info` (stack trace) and `operation-id`. A `condition` field on the failure types would therefore require parsing the message head on the warehouse path; decide separately whether that is worth it alongside PySpark's `getCondition()` on the Spark path.

Gated on a richer observation source: the reader parses catalog DDL type strings, which do not carry nested NOT NULL; observing the real `StructType` (e.g. `spark.table(...).schema`) would round-trip it faithfully. Then decide whether nested-field changes stay blocked (accurately reported) or become actionable. See the type-model fidelity section of explanation-architecture.md.

- [x] Compile empty column comments as `COMMENT ''` — SQL warehouses reject `ALTER TABLE ... ALTER COLUMN ... UNSET COMMENT` (verified live 2026-07-12). RESOLVED 2026-07-14: the fix from PR #213 reapplied as its own PR (the UNSET branch deleted; an empty desired comment compiles to `COMMENT ''` unconditionally) and the lifecycle live test's `account_code` empty-comment transition restored.
- [ ] The reader cannot round-trip struct field names containing special characters (found by the live suite 2026-07-12). With column mapping, the declaration gate and compiler happily create `s STRUCT<`bad name`: INT>`, but information_schema renders the type unquoted (`struct<bad name:int>`), the shared type parser skips the column as unrecognised (with a warning), and the next sync plans an `ADD COLUMN s` that fails `FIELD_ALREADY_EXISTS`. Either teach the parser quoted/special-character field names or make the declaration gate reject special characters in NESTED field names regardless of column mapping until the round trip works.
- [x] Renames need an identity signal beyond the name (parked 2026-07-08). RESOLVED 2026-07-12 via the `renamed_from` hint on `Column`: the differ relabels the observed column through the hint and emits `RenameColumn` directly; the hint is inert once applied. An ambiguous declared rename (old and new both present) is the non-action `ColumnRenameConflict` difference rejected by the `AmbiguousColumnRename` policy rule; editing a name directly without the hint is taken literally as `DropColumn` plus `AddColumn` (no rename guessing). Table renames would extend the same mechanism (`renamed_from` on `DeltaTable`), not yet built.
- [x] Live-workspace verification for column renames. RESOLVED 2026-07-14 (manual notebook check against a real workspace): (1) Unity Catalog column tags and comments travel with `ALTER TABLE ... RENAME COLUMN` (tag observed under the new name, comment intact), so the differ's projected comparison is correct and a rename converges in a single sync; (2) a dependent CHECK constraint blocks the rename with `DELTA_CONSTRAINT_DEPENDENT_COLUMN_CHANGE` — a clean execution error, per the no-preflight policy; (3) the original suppression question is obsolete (the plan states PK/FK drops explicitly since the explicit-drops refactor), and the underlying hazard is confirmed real: a direct `RENAME COLUMN` on a PK column with a live inbound FK succeeds and silently drops both the PK and the other table's FK, while the engine's bare `DROP PRIMARY KEY IF EXISTS` fails closed first (`DependentConstraintsExistException`: "Cannot delete constraint ... with non empty child constraints"). Also verified: the engine's exact three-statement PK-rename sequence (drop key, rename, re-add key) executes end-to-end, and a partition-column rename leaves data and partition layout intact. Residual unknown: governed tags (docs say they block `DROP COLUMN`; behaviour under a rename is untested — the verified travel was a regular tag).
- [ ] Cross-catalog inbound foreign keys are invisible to `PrimaryKeyReferencedByForeignKeys` (information_schema is per-catalog), so a cross-catalog referenced PK drop still fails at execution rather than validation. Decide whether that is acceptable long-term or worth probing the referencing catalogs (cost: catalog reads fan out). The outbound direction is rejected at declaration for the same reason (`ForeignKey` requires the referenced table to share the owner's catalog); lifting either restriction means resolving the parent side from the parent's catalog or the metastore-wide `system.information_schema`.
- [ ] Watch the inbound-FK read cost: observing referencing foreign keys adds one information_schema query per table read (PR #152). No latency evidence yet — do not optimize without it; if large syncs hurt, batch the metadata reads per catalog rather than per table.
- [ ] Release notes for the next release must call out the stricter property values: previously-accepted declarations like `"True"`, `"1_000"`, or compound intervals (`interval 1 hour 30 minutes`) now fail at declaration time with messages naming the expected format. Also call out two breaking declaration changes from the FK-pairing redesign: `primary_key` moved from a per-column `Column(primary_key=True)` flag to a `DeltaTable(primary_key=[...])` parameter, and `ForeignKey(columns=...)` replaces the positional `local_columns=[...]` parameter. The new `columns` form accepts a string for a single-column parent key, a sequence for a same-name key, or an explicit `{local: referenced}` mapping for an ambiguous composite key; the old `local_columns` keyword fails loudly as an unexpected argument rather than silently changing meaning. Also call out: `delta.enableTypeWidening` is now a managed key — per the registry admission policy this is breaking, since tables with the key set but undeclared start failing validation (`PropertyMustBeDeclared`) on upgrade.

- [ ] Make the application layer backend-agnostic, not just backend-library-free. Today the `backend-imports-stay-in-adapters` contract only forbids importing the `delta`/`pyspark` _packages_; the application layer still hardcodes Delta-family _policy_ — the safe-change rules (`PartitioningChangeNotSupported`, `ColumnDataTypeChangeNotSupported`, `NonNullableColumnAdd`, `ColumnMappingRequiredForDrop`) exist because Databricks/Delta rejects those operations, and `application/properties.py` holds the Delta property catalogue (`DELTA_PROPERTY_POLICY`, `Property`, and the `delta.*` key strings) consumed by `validation.py`, `api/delta_table.py`, and the reader. The layering is sound for now (application is the only layer all three consumers can reach without violating the `adapters|api → application → domain` order), but it means "backend-agnostic" is only half true. The real refactor: `application` holds only the _mechanism_ (how rules run, the `Rule` protocol, how `validate_diff` composes them), and the backend _specifics_ (which rules, which property keys and their restrictions) are injected from the composition root or an adapter-provided port. This must move ALL the backend-flavoured rules and the property catalogue together — moving only the property pieces just relocates a third of the problem. Larger change, own PR. See the property-ownership spec addendum for how the registry ended up in application.

- [ ] Review the casefold enforcement on declared identifiers (noted 2026-07-13 during the PR #215 review). Today the domain _rejects_ any declared identifier that is not casefold-stable — column names and struct field names, qualified names, layout keys, and `renamed_from` (PR #215) — while the reader adapters _normalise_ observed identifiers by casefolding (`adapters/databricks/sql/rows.py`, `parse.py`). The `Column` docstring now states that current behaviour rather than claiming normalization, but the policy still needs a decision: (1) reject vs normalise on the declared side; (2) the "must be lowercase" message actually enforces `x == x.casefold()`, which is not the same invariant — a legitimately lowercase name like `straße` fails the check (`'ß'.casefold() == 'ss'`), and an observed `straße` casefolds to `strasse` on read, a name the compiler would then quote differently than the catalog stores; (3) verify the policy against Unity Catalog's actual identifier-case semantics (case-insensitive but case-preserving) rather than assuming ASCII lowering.
- [ ] Spark variable substitution corrupts `${...}` in declared free-text on the spark backend (found 2026-07-17 during the PR #254 property-test review; deferred as not a pressing possibility). Spark applies `spark.sql.variable.substitute` (default `true`) to the whole SQL text _before_ lexing, so `${...}` inside a single-quoted literal is rewritten and `quote_literal` (`adapters/databricks/sql/dialect.py`) cannot defend against it — the rewrite happens before quotes mean anything. Confirmed on local pyspark 4 (Spark session per `tests/conftest.py`): `SELECT '${no_such_var}'` → `''` (silent corruption), `SELECT '${env:HOME}'` → the driver's `HOME` (environment leak into catalog metadata), `'${spark.sql.shuffle.partitions}'` can throw, and a DDL `COMMENT '${env:HOME}'` stores the resolved path. The exposure is any user-declared free-text executed through `spark.sql`: table/column comments, tag values/keys, table-property values/keys. Nuance: only the no-spaces form substitutes — `${a b}` and `${}` pass through verbatim — so a blunt "reject any `${`" rule would over-block. The engine never emits `${...}`; the string is always the user's declared value passed through verbatim, so the trigger is a human typing `${...}` in a comment/tag/property (plausible via dbt `persist_docs`, Databricks job-parameter references, or templated paths, but judged low-frequency for now). Recommended fix when picked up: route all spark SQL through one adapter-level runner that disables `spark.sql.variable.substitute` around execution (gate on the `${` substring so the common clean path never mutates session state; set-and-restore via try/finally; fail closed — do not execute — if the conf cannot be set), keeping the Spark quirk at the adapter boundary rather than leaking it into a backend-free validation rule. Open question before any warehouse-side change: whether the SQL-warehouse backend (databricks-sql-connector / DBSQL) substitutes at all — hypothesis is it takes `${...}` verbatim since substitution is a Spark-session feature, but this needs a one-off live check (`SELECT '${env:HOME}'` via the warehouse cursor + an engine-level sync of a `${...}` comment/tag/property read back verbatim) through the Live workflow before deciding. Regression coverage to add alongside the fix: a curated `${...}` payload in `tests/adapters/databricks/sql/strategies.py` `SQL_LITERAL_VALUES` and an `@example` pin on the `test_dialect.py` spark round-trip test (both currently live only on the PR #254 branch — adding the payload before the fix makes the spark round-trip fail, since substitution is still live).
