- [ ] The reader cannot round-trip struct field names containing special characters (found by the live suite 2026-07-12). With column mapping, the declaration gate and compiler happily create `s STRUCT<`bad name`: INT>`, but information_schema renders the type unquoted (`struct<bad name:int>`), the shared type parser skips the column as unrecognised (with a warning), and the next sync plans an `ADD COLUMN s` that fails `FIELD_ALREADY_EXISTS`. Either teach the parser quoted/special-character field names or make the declaration gate reject special characters in NESTED field names regardless of column mapping until the round trip works.
- [x] Renames need an identity signal beyond the name (parked 2026-07-08). RESOLVED 2026-07-12 via the `renamed_from` hint on `Column`: the differ relabels the observed column through the hint and emits `RenameColumn` directly; the hint is inert once applied. An ambiguous declared rename (old and new both present) is the non-action `ColumnRenameConflict` difference rejected by the `AmbiguousColumnRename` policy rule; editing a name directly without the hint is taken literally as `DropColumn` plus `AddColumn` (no rename guessing). Table renames would extend the same mechanism (`renamed_from` on `DeltaTable`), not yet built.
- [x] Live-workspace verification for column renames. RESOLVED 2026-07-14 (manual notebook check against a real workspace): (1) Unity Catalog column tags and comments travel with `ALTER TABLE ... RENAME COLUMN` (tag observed under the new name, comment intact), so the differ's projected comparison is correct and a rename converges in a single sync; (2) a dependent CHECK constraint blocks the rename with `DELTA_CONSTRAINT_DEPENDENT_COLUMN_CHANGE` — a clean execution error, per the no-preflight policy; (3) the original suppression question is obsolete (the plan states PK/FK drops explicitly since the explicit-drops refactor), and the underlying hazard is confirmed real: a direct `RENAME COLUMN` on a PK column with a live inbound FK succeeds and silently drops both the PK and the other table's FK, while the engine's bare `DROP PRIMARY KEY IF EXISTS` fails closed first (`DependentConstraintsExistException`: "Cannot delete constraint ... with non empty child constraints"). Also verified: the engine's exact three-statement PK-rename sequence (drop key, rename, re-add key) executes end-to-end, and a partition-column rename leaves data and partition layout intact. Residual unknown: governed tags (docs say they block `DROP COLUMN`; behaviour under a rename is untested — the verified travel was a regular tag).
- [ ] Cross-catalog inbound foreign keys are invisible to `PrimaryKeyReferencedByForeignKeys` (information_schema is per-catalog), so a cross-catalog referenced PK drop still fails at execution rather than validation. Decide whether that is acceptable long-term or worth probing the referencing catalogs (cost: catalog reads fan out). The outbound direction is rejected at declaration for the same reason (`ForeignKey` requires the referenced table to share the owner's catalog); lifting either restriction means resolving the parent side from the parent's catalog or the metastore-wide `system.information_schema`.
- [ ] Watch the inbound-FK read cost: observing referencing foreign keys adds one information_schema query per table read (PR #152). No latency evidence yet — do not optimize without it; if large syncs hurt, batch the metadata reads per catalog rather than per table.
- [ ] Release notes for the next release must call out the stricter property values: previously-accepted declarations like `"True"`, `"1_000"`, or compound intervals (`interval 1 hour 30 minutes`) now fail at declaration time with messages naming the expected format. Also call out two breaking declaration changes from the FK-pairing redesign: `primary_key` moved from a per-column `Column(primary_key=True)` flag to a `DeltaTable(primary_key=[...])` parameter, and `ForeignKey(columns=...)` replaces the positional `local_columns=[...]` parameter. The new `columns` form accepts a string for a single-column parent key, a sequence for a same-name key, or an explicit `{local: referenced}` mapping for an ambiguous composite key; the old `local_columns` keyword fails loudly as an unexpected argument rather than silently changing meaning. Also call out: `delta.enableTypeWidening` is now a managed key — per the property-policy admission rule this is breaking, since tables with the key set but undeclared start failing validation (`PropertyMustBeDeclared`) on upgrade.

- [ ] Make the application layer backend-agnostic, not just backend-library-free. Today the `backend-imports-stay-in-adapters` contract only forbids importing the `delta`/`pyspark` _packages_; the application layer still hardcodes Delta-family _policy_ — the safe-change rules (`PartitioningChangeNotSupported`, `ColumnDataTypeChangeNotSupported`, `NonNullableColumnAdd`, `ColumnMappingRequiredForDrop`) exist because Databricks/Delta rejects those operations, and `application/properties.py` holds the Delta property policy (`DELTA_PROPERTY_POLICY`, `Property`, and the `delta.*` key strings) consumed by `validation.py`, `api/delta_table.py`, and the reader. The layering is sound for now (application is the only layer all three consumers can reach without violating the `adapters|api → application → domain` order), but it means "backend-agnostic" is only half true. The real refactor: `application` holds only the _mechanism_ (how rules run, the `SafetyRule` protocol, how `validate_diff` composes them), and the backend _specifics_ (which rules, which property keys and their restrictions) are injected from the composition root or an adapter-provided port. This must move ALL the backend-flavoured rules and the property policy together — moving only the property pieces just relocates a third of the problem. Larger change, own PR. See the property-ownership spec addendum for why the policy currently lives in application.

- [ ] Decide whether to emit `RELY` on FK/PK constraints. Without `RELY`, Databricks treats informational constraints as documentation only and the optimizer cannot use them for join elimination / query rewrite. - [ ] Review the casefold enforcement on declared identifiers (noted 2026-07-13 during the PR #215 review). Today the domain _rejects_ any declared identifier that is not casefold-stable — column names and struct field names, qualified names, layout keys, and `renamed_from` (PR #215) — while the reader adapters _normalise_ observed identifiers by casefolding (`adapters/databricks/sql/rows.py`, `parse.py`). The `Column` docstring now states that current behaviour rather than claiming normalization, but the policy still needs a decision: (1) reject vs normalise on the declared side; (2) the "must be lowercase" message actually enforces `x == x.casefold()`, which is not the same invariant — a legitimately lowercase name like `straße` fails the check (`'ß'.casefold() == 'ss'`), and an observed `straße` casefolds to `strasse` on read, a name the compiler would then quote differently than the catalog stores; (3) verify the policy against Unity Catalog's actual identifier-case semantics (case-insensitive but case-preserving) rather than assuming ASCII lowering.
- [x] Spark variable substitution corrupting `${...}` in declared free text. RESOLVED 2026-07-22: the backend-private `SparkSqlRunner` is the sole production caller of `spark.sql`, shared by the reader and executor. SQL without `${` takes the unchanged fast path; for SQL containing it, the runner disables `spark.sql.variable.substitute` for the call and restores the original setting in `finally`, leaves an already-disabled session untouched, and refuses to execute if the guard cannot be installed. A local engine regression enables substitution, syncs table and column comments containing `${env:HOME}`, reads both back verbatim, confirms the setting was restored, and confirms a second sync is a no-op.
