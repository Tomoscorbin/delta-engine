- [x] Live-workspace verification for column renames. RESOLVED 2026-07-14 (manual notebook check against a real workspace): (1) Unity Catalog column tags and comments travel with `ALTER TABLE ... - [ ] Cross-catalog inbound foreign keys are invisible to `PrimaryKeyReferencedByForeignKeys` (information_schema is per-catalog), so a cross-catalog referenced PK drop still fails at execution rather than validation. Decide whether that is acceptable long-term or worth probing the referencing catalogs (cost: catalog reads fan out). - [ ] Release notes for the next release must call out the stricter property values: previously-accepted declarations like `"True"`, `"1_000"`, or compound intervals (`interval 1 hour 30 minutes`) now fail at declaration time with messages naming the expected format. Also call out two breaking declaration changes from the FK-pairing redesign: `primary_key` moved from a per-column `Column(primary_key=True)` flag to a `DeltaTable(primary_key=[...])` parameter, and `ForeignKey(columns=...)` replaces the positional `local_columns=[...]` parameter. The new `columns` form accepts a string for a single-column parent key, a sequence for a same-name key, or an explicit `{local: referenced}` mapping for an ambiguous composite key; the old `local_columns` keyword fails loudly as an unexpected argument rather than silently changing meaning. Also call out: `delta.enableTypeWidening` is now a managed key — per the property-policy admission rule this is breaking, since tables with the key set but undeclared start failing validation (`PropertyMustBeDeclared`) on upgrade.

- [ ] Make the application layer backend-agnostic, not just backend-library-free. Today the `backend-imports-stay-in-adapters` contract only forbids importing the `delta`/`pyspark` _packages_; the application layer still hardcodes Delta-family _policy_ — the safe-change rules (`PartitioningChangeNotSupported`, `NonWideningColumnTypeChange`, `NonNullableColumnAdd`, `ColumnMappingRequiredForDrop`) exist because Databricks/Delta rejects those operations, and `application/properties.py` holds the Delta property policy (`DELTA_PROPERTY_POLICY`, `Property`, and the `delta.*` key strings) consumed by `validation.py`, `api/delta_table.py`, and the reader. The layering is sound for now (application is the only layer all three consumers can reach without violating the `adapters|api → application → domain` order), but it means "backend-agnostic" is only half true. The real refactor: `application` holds only the _mechanism_ (how rules run, the `SafetyRule` protocol, how `validate_diff` composes them), and the backend _specifics_ (which rules, which property keys and their restrictions) are injected from the composition root or an adapter-provided port. This must move ALL the backend-flavoured rules and the property policy together — moving only the property pieces just relocates a third of the problem. Larger change, own PR. See the property-ownership spec addendum for why the policy currently lives in application.
