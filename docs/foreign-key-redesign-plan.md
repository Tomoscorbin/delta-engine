# Foreign key redesign implementation plan

## Status

Draft implementation plan for a future foreign-key redesign. This document records the target design, migration path, and test/documentation work before code changes begin.

## Problem

The current foreign-key model is stringly typed in the place where it most needs structure:

- `ForeignKeyConstraint.references` is a `str` containing a dotted `catalog.schema.table` name.
- The Databricks SQL compiler reparses that string with `foreign_key.references.split(".")`, while every other fully qualified table name is rendered through `QualifiedName` and `backtick_qualified_name()`.
- Dependency resolution and failure reporting also compare referenced tables as strings.
- The public API exports the internal domain object as `ForeignKey`, exposing `constraint_name` even though desired-side constraint names are generated by the engine.
- `SetForeignKey` carries a full `ForeignKeyConstraint` whose `constraint_name` is optional, so the compiler has to assert a lifecycle invariant instead of receiving compiler-ready data.

The result is a shallow interface: callers and downstream layers must know implementation details such as dotted-string format, generated names, and partially initialized constraints.

## Design goals

1. Represent table names structurally in the domain.
2. Keep string parsing at the API and adapter boundaries.
3. Make the SQL compiler a mechanical renderer, not a parser or validator.
4. Hide generated constraint names from the public foreign-key declaration API.
5. Make plan actions operational and compiler-ready.
6. Preserve a migration path for existing callers that pass `references="catalog.schema.table"`.
7. Prefer a deep, Ousterhoutian API: simple declarations outside, rich validated objects inside.

## Non-goals

- Implement user-defined FK constraint names in this redesign. The new API should not expose `constraint_name`; a separate future feature can add explicit naming if needed.
- Inline foreign keys into `CREATE TABLE`. FK constraints should remain separate plan actions because self-referential FKs and dependency-resolution failure propagation are easier and more uniform when each FK is an independently applicable action.
- Add unique-key support. The resolver can continue to require referenced columns to match the referenced table primary key until unique constraints are modeled.
- Change Databricks enforcement semantics. Constraints remain informational unless a later `RELY` design is adopted.

## Target design

### 1. Add structured FK target values

Introduce a domain value object for the referenced key:

```python
@dataclass(frozen=True, slots=True)
class ReferencedKey:
    table: QualifiedName
    columns: tuple[str, ...]
```

Then change the internal FK constraint to reference that value:

```python
@dataclass(frozen=True, slots=True)
class ForeignKeyConstraint:
    local_columns: tuple[str, ...]
    references: ReferencedKey
    constraint_name: str | None = None
```

`ForeignKeyConstraint.signature` becomes:

```python
(self.local_columns, self.references.table, self.references.columns)
```

This keeps content identity independent of constraint name while eliminating dotted-string parsing from the domain and compiler.

Alternative considered: store `referenced_table: QualifiedName` and `referenced_columns: tuple[str, ...]` directly on `ForeignKeyConstraint`. That is less disruptive, but `ReferencedKey` better names the domain concept: a foreign key references a key, not merely a table.

### 2. Add `QualifiedName.parse()`

Add a small constructor for boundary parsing:

```python
@dataclass(frozen=True, slots=True)
class QualifiedName:
    ...

    @classmethod
    def parse(cls, raw: str) -> Self:
        parts = raw.split(".")
        if len(parts) != 3:
            raise ValueError(...)
        return cls(*parts)
```

`QualifiedName.__post_init__` should remain the single source for blank/lowercase validation. Boundary code can use `QualifiedName.parse()` instead of duplicating dotted-name validation.

### 3. Separate public FK declarations from internal constraints

Stop exporting `ForeignKeyConstraint` as the public `ForeignKey`. Add a public API declaration object, likely in `src/delta_engine/api/foreign_key.py`:

```python
@dataclass(frozen=True, slots=True)
class ForeignKey:
    local_columns: tuple[str, ...]
    references: str | QualifiedName | DeltaTable
    referenced_columns: tuple[str, ...] | None = None
```

The public object should not expose `constraint_name`.

`DeltaTable` lowers public declarations into internal `ForeignKeyConstraint` instances before building `DesiredTable`:

- If `references` is a `str`, parse it with `QualifiedName.parse()` and require `referenced_columns`.
- If `references` is a `QualifiedName`, use it and require `referenced_columns`.
- If `references` is a `DeltaTable`, use `references.to_desired_table().qualified_name`; when `referenced_columns` is omitted, infer it from `references.primary_key`.
- If the referenced table has no primary key and `referenced_columns` is omitted, raise a clear `ValueError`.

Preferred public usage:

```python
customers = DeltaTable(
    catalog="dev",
    schema="silver",
    name="customers",
    columns=[Column("id", Integer(), nullable=False, primary_key=True)],
)

orders = DeltaTable(
    catalog="dev",
    schema="silver",
    name="orders",
    columns=[
        Column("order_id", Integer(), nullable=False, primary_key=True),
        Column("customer_id", Integer(), nullable=False),
    ],
    foreign_keys=[
        ForeignKey(local_columns=("customer_id",), references=customers),
    ],
)
```

String references should remain supported for forward references, cross-module declarations, and references to tables that are not available as `DeltaTable` objects:

```python
ForeignKey(
    local_columns=("customer_id",),
    references="dev.silver.customers",
    referenced_columns=("id",),
)
```

### 4. Make `SetForeignKey` compiler-ready

Change the plan action from carrying the full domain constraint:

```python
@dataclass(frozen=True, slots=True)
class SetForeignKey(Action):
    foreign_key: ForeignKeyConstraint
```

to carrying the exact data needed to render the operation:

```python
@dataclass(frozen=True, slots=True)
class SetForeignKey(Action):
    local_columns: tuple[str, ...]
    referenced_table: QualifiedName
    referenced_columns: tuple[str, ...]
    constraint_name: str
```

Then `_diff_foreign_keys()` becomes responsible for projecting a desired, named domain constraint into this action. The compiler no longer needs to assert that `constraint_name` is non-`None`.

The Databricks compiler becomes:

```python
@_compile_action.register
def _(action: SetForeignKey, backticked_table_name: str) -> str:
    constraint = backtick(action.constraint_name)
    local_cols = ", ".join(backtick(col) for col in action.local_columns)
    ref_cols = ", ".join(backtick(col) for col in action.referenced_columns)
    ref_table = backtick_qualified_name(action.referenced_table)
    return (
        f"ALTER TABLE {backticked_table_name}"
        f" ADD CONSTRAINT {constraint}"
        f" FOREIGN KEY ({local_cols}) REFERENCES {ref_table} ({ref_cols})"
    )
```

This makes `SetForeignKey` symmetric with `SetPrimaryKey`: both actions carry non-optional constraint names and compiler-ready fields.

## Test checklist

Add or update coverage for:

- `QualifiedName.parse()` validation.
- `ReferencedKey` validation.
- `ForeignKeyConstraint.signature` using structured references.
- Databricks reader constructs `ReferencedKey`/`QualifiedName` correctly.
- Dependency resolver orders tables using structured referenced names.
- FK failure messages still render readable qualified names.
- `SetForeignKey` action has non-optional compiler-ready fields.
- SQL compiler uses `backtick_qualified_name()` for referenced tables.
- Public `ForeignKey` has no `constraint_name` parameter.
- `ForeignKey(references=DeltaTable)` infers the referenced primary key.
- Missing primary key during inference raises a clear error.
- String/`QualifiedName` references require `referenced_columns`.
- Composite FK declarations preserve local/referenced column order.
- Existing drift behavior remains unchanged: FKs match by content, not name.

## Migration notes

Potentially breaking changes:

- `ForeignKey.references` no longer exposes a raw string internally.
- Public `ForeignKey` no longer accepts or exposes `constraint_name`.
- Tests or downstream code importing `ForeignKeyConstraint as ForeignKey` will need to import the public API object instead.

Mitigation options:

1. Provide a short deprecation window where `DeltaTable.foreign_keys` accepts both public `ForeignKey` and domain `ForeignKeyConstraint`.
2. Keep `ForeignKeyConstraint` importable from `delta_engine.domain.model` for internal/advanced use, but remove it from the top-level curated API.
3. Mention the migration in docs and release notes:
   - replace `references="cat.sch.table"` with either `references=table` or keep the string and provide `referenced_columns`;
   - remove `constraint_name` from declarations.

## Open decisions

1. Should `ForeignKey(references=QualifiedName(...))` require `referenced_columns`, or should it be resolvable against the registry later? Initial recommendation: require columns because a `QualifiedName` alone does not carry primary-key metadata.
2. Should `ForeignKey(references="cat.sch.table")` be parsed immediately in the API object or delayed until `DeltaTable` lowers declarations? Initial recommendation: parse during lowering so the API object remains a lightweight declaration.
3. Should dependency resolution store graph keys as `QualifiedName` instead of `str` end-to-end? Initial recommendation: yes, except where a string is needed for display or stable dictionary output.
4. Should `ReferencedKey` validate duplicate referenced columns? Initial recommendation: yes, because duplicate referenced columns are not a coherent FK target.
5. Should `DeltaTable.foreign_keys` return public declarations or internal named constraints? Initial recommendation: continue returning the internal desired constraints from `to_desired_table()`, but consider making the public `DeltaTable.foreign_keys` property return declarations if the API should avoid exposing generated names completely.

## Recommended sequence for a PR

1. Add `QualifiedName.parse()` and `ReferencedKey`.
2. Convert `ForeignKeyConstraint` and all internal consumers to structured references.
3. Redesign `SetForeignKey` and simplify the compiler.
4. Add the new public `ForeignKey` declaration and lowering logic in `DeltaTable`.
5. Update docs and public API exports.
6. Run the full test suite and perform a final sweep for lingering `.references.split(".")` or string comparisons against FK referenced tables.

The end state should be: users declare foreign keys simply, the domain carries structured validated names, the planner emits complete operations, and the SQL compiler renders without parsing or asserting lifecycle details.
